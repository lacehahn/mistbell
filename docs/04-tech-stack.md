# 技术选型

> 状态：实现前建议，不创建工程、代码、数据文件或依赖。本轮只定义将来的实现与验收方式。
> 假设：2 人小团队，其中 1 人能承担 C#、基础着色器与渲染调试，另 1 人承担 Blender／像素资产与资料；实际能力见 D04。
> ⚠️ **能力修正（2026-11-01）**：团队**当前无游戏引擎经验**（D01 定稿时确认）。本文件中所有 C#／着色器／渲染调试工时，都是"有经验者"的估算，不能直接当作新手的工期；D04 的 8 周 / 320 人时须在 M1 前按实际学习曲线重估，或先执行下面的 3 天管线 spike 再定排期。
> 引擎能力与授权资料核查于 2026-11-01；性能、工时、硬件与资源数均为本项目设计预算，尚未实测。

## 1. 明确推荐：Unity 6 LTS + URP

推荐 **Unity 6 LTS、URP 的 3D Renderer、单台场景相机**。角色作为 3D 空间中的 Billboard 像素贴片，与教堂共用深度和光雾；不用 2D Renderer 再拼接一套独立 3D 画面。理由是本项目的主要难点为受控相机、建筑近读、混合遮挡和外部文本，并非大规模动态光照。

✅ **已定（2026-11-01）D01**：引擎与版本锁定为 **Unity 6.3 LTS（6000.3）**，补丁 **6000.3.27f1**（2026-10-20，LTS 支持至 2027-12-04），渲染管线 **URP 3D Renderer**。定稿理由：①团队无引擎经验，决定产能的是生态、教程密度与 Windows 打包成熟度，Unity 在这三项上优势最大；②本项目的技术难点是受控相机、建筑近读、混合遮挡与外部文本驱动，属于工程活而非光照活，Unity 的 C#／UI／数据读取链路最短；③UE 的体积光雾优势改用「3 层雾片 + 局部光雾缓冲」降级方案替代，M1 只给最多 8 人时验证，超时即降级、不切引擎。Godot 4 与 Unreal 5 作为记录保留，不再并行做原型。

⚠️ 版本纪律：Unity 6.0 LTS 已于 2026-10 EOL，**凡引用 6.0 手册的接口结论一律按 6000.3 手册复核**后才可开工；Unity 6.4–6.6 属于 Supported Update 流（生命期只到下个版本发布），不得用于生产分支。升级只允许发生在里程碑边界，并重跑混合遮挡与揭示镜头的回归。

### 引擎比较

以下难度是依据本项目范围作的工程判断，不是通用排名；各引擎都能做 HD-2D，不能以「能导入像素图」等同于完成风格。Unreal 侧以 **UE 5.8**（2026-10-22 发布，当前版本）为参照，5.7 仍在支持期内。

| 维度 | Unity（URP） | Godot 4 | Unreal 5 |
| --- | --- | --- | --- |
| HD-2D 实现难度 | 中：基础混合容易，局部体积雾和带状模糊需自定义；适合有限镜头 | 中：Sprite3D 与 3D 共存直接，风格化后期仍需渲染能力 | 中偏高：光雾基础强，但像素清晰度、抗锯齿和曝光需专门约束 |
| 2D＋3D 混合 | 3D 面片／SpriteRenderer 放入 3D Renderer，补深度、受光与遮挡规范 | Sprite3D 支持 3D 世界中的图集贴片，朝向与遮挡仍需测试 | Paper 2D 支持精灵与 Flipbook 混合 3D；不能默认其材质满足本项目受光要求 |
| 后期管线 | 原生 Bloom、调色、景深；自定义 Render Pass 做保护遮罩与移轴感；URP 无 HDRP 同级原生局部体积雾 | Forward+ 有体积雾；Compositor 可扩展后期，但不是无需技术能力的编辑器开关 | 原生体积雾和电影镜头工具较全；本项目无需默认开启 Lumen、Nanite 或复杂时域方案 |
| Blender 管线 | FBX＋外部纹理；材质手动映射到 URP，导入预设较易统一 | 推荐 glTF 2.0／GLB；直接导入 blend 会调用 Blender，构建机需考虑工具依赖 | FBX 静态网格成熟；材质仍需转换，单位和碰撞命名另定规范 |
| 团队能力 | 若具备 C# 与基础图形调试，最易把文本、相机、UI 与渲染接在一起 | 若已有 GDScript／Godot 经验可缩短上手，但不能省去渲染验证 | 若已有 Blueprint／材质与 UE 制作经验可降低成本；本轮不假定已具备 |
| macOS 开发／Windows 验证 | Metal 开发，Windows DX11 独立验证；平台 shader 与压缩需分别检查；**Windows 包只能 Mono（IL2CPP 不可跨平台编译）** | 需验证选用渲染器在 Mac 和 Windows 上的一致性，不能从 Compatibility 推断 Forward+ | Mac 可开发，且**支持从 macOS 交叉编译 Win64 包**（自带工具链）——这是相对 Unity 的实际优势；但仍须真 Windows 机器验画面与性能，转译层不算数 |
| 发行成本 | 符合 Personal 条件时引擎许可可为 0；超过门槛需付订阅；Runtime Fee 已取消 | MIT，可商业发行、无引擎收入分成；需保留许可与第三方声明 | 单产品终身总收入 100 万美元以内免费；超出部分 5% 版税；若同期在 Epic 商店首发可降至 3.5%；游戏类无席位费 |
| 本项目结论 | **已选**（D01 已定）：以受限雾方案换取可控产能、生态与打包成熟度 | 记录保留：适合已有 GDScript／Godot 经验、或把许可确定性放在第一位的团队 | 记录保留：**《歧路旅人》本体即由 Acquire 以 UE4 开发（峰值 6 名程序）**，说明该风格的光雾栈确实在 UE 上最顺；但像素清晰度、抗锯齿与打包成本对本规模不利，故不选 |

能力依据：[Unity 6.3 渲染管线功能表](https://docs.unity3d.com/6000.3/Documentation/Manual/render-pipelines-feature-comparison.html)、[Godot Sprite3D](https://docs.godotengine.org/en/stable/classes/class_sprite3d.html)、[Godot 体积雾](https://docs.godotengine.org/en/stable/tutorials/3d/volumetric_fog.html)、[Godot Compositor](https://docs.godotengine.org/en/stable/tutorials/rendering/compositor.html)、[Unreal Paper 2D](https://dev.epicgames.com/documentation/unreal-engine/paper-2d-in-unreal-engine?application_version=5.2)、[Unreal 体积雾](https://dev.epicgames.com/documentation/en-us/unreal-engine/volumetric-fog-in-unreal-engine)、[Acquire 访谈：歧路旅人的 HD-2D 与 UE4 管线](https://www.unrealengine.com/spotlights/octopath-traveler-s-hd-2d-art-style-and-story-make-for-a-jrpg-dream-come-true)。Godot 体积雾限 Forward+，Compositor 的渲染器支持范围也有限；这影响低配降级，不能统一写成「所有模式都有」。参考作的实际管线（UE4）只用于解释风格成因，不构成本项目选型依据。

### 为什么不是 UE：逐项论证（2026-11-01 追加）

D01 定稿后仍会被反复追问「《歧路旅人》就是 UE 做的，为什么不选 UE」。这里给出量化比较，避免用传闻拍板。

权重是本项目的判断：2 人、无引擎经验、Mac 开发、Windows 优先、文本驱动的 12–16 分钟体验。

| 维度 | 权重 | Unity 6.3 + URP | UE 5.8 |
| --- | --- | --- | --- |
| 学习曲线与「卡住时能不能搜到答案」 | 25% | 9／10：C# 与 URP 资料密度最高，中文问答充足 | 5／10：Blueprint 起步快，但 UMG／资产系统／C++ 编译链更重，零经验时无人可问的概率高 |
| HD-2D 画面达成成本 | 25% | 6／10：需自写带状移轴与局部光雾两个 Pass | 9／10：tilt-shift DoF、Bloom、体积雾、Sequencer、Niagara 开箱即用 |
| Mac → Windows 出包 | 15% | 5／10：只能 Mono，IL2CPP 需 Windows 机器 | 8／10：自带工具链可交叉编译 Win64 |
| 文本／数据驱动内容 | 15% | 9／10：TMP ＋ JSON ＋ C# 最直接 | 5／10：UMG ＋ DataTable，长文排版与本地化管线更重 |
| 迭代速度与包体 | 10% | 8／10：热重载快，包体 100–300 MB | 5／10：shader 编译与 C++ 重编慢，空包 1 GB 级 |
| 授权与成本 | 10% | 9／10：Personal 门槛内为 0 | 7／10：100 万美元以内 0，之上 5%（Epic 首发 3.5%） |

加权结果：**Unity 7.5 / UE 6.9**（自评，误差 ±0.5）。画面这一项 UE 领先 3 分，但被「学习曲线 + 文本驱动 + 迭代速度」合计 50% 的权重抵消。

**UE 做像素风格的具体代价**（不是「太重」这种空话）：
- TAA／TSR 会把像素 art 抹糊：必须关闭时域抗锯齿、锁 100% 屏幕百分比、关自动曝光，否则角色边缘永远在半像素间抖动；
- 后处理是全局的：「只在揭示方向约 80 m 有雾」需要改后处理材质或做 stencil 分层，并不比 URP 的 RendererFeature 省事，只是换了种写法；
- 包体与启动：空场景 Windows 包即 GB 级，Mac 上编辑器常驻内存显著高于 Unity（32 GB 够用但无余量）。

**什么情况下应该改选 UE（触发条件，供将来复核）**
1. spike 第 3 天在 URP 上超时或达不到 1080p／60 fps，且降级为全屏 tilt-shift 后画面不可接受；
2. 团队中出现 UE 经验 ≥ 1 年的人，或愿意先投入 80 人时专职学 UMG／Sequencer；
3. 发行目标改为「画面为王」的买断制并在 Steam 争首页可见度，愿意承担 5% 版税与更大包体。

三条同时成立才重开 D01；任一条单独成立只作为局部降级处理，不构成换引擎的理由。

**《歧路旅人》证据的正确解读**：那款游戏峰值有 6 名程序员。对两人零经验团队，这不是「小团队也能做」的论据，而是「有 6 名熟练程序员才把它做得又快又好」。参考作的价值在于说明观感如何构成，不在于证明引擎门槛低。

### D01 落地前的 3 天管线 spike（团队无引擎经验，必做）

目的：在写任何游戏逻辑前，用一个**可抛弃**的最小工程证明「Blender → Unity → 目标包」这条链路真的成立。工程不进主仓库，3 天后连测试结论一起归档，只保留记录。

| 天 | 验证项 | 通过标准 | 不通时的退路 |
| --- | --- | --- | --- |
| 1 | Blender 教堂外壳（约 2 万面简化体）→ FBX → URP：单位／朝向／缩放、材质映射到 URP Lit、法线与 UV | Unity 内比例与 Blender 一致（1 m = 1 unit），石材无黑面／翻面；同一套材质设置能在 6 小时内第二次复现 | 改用 Unity 的 glTF 导入包；或在 Blender 内烘顶点色／顶点 AO 兜底 |
| 2 | 光照烘焙（Lightmap）＋混合遮挡：Billboard 像素角色与 3D 建筑的前后关系 | 用 Generate Lightmap UVs 烘焙无接缝、无漏光；角色走到石柱后与门内时被正确遮挡，不出现整片贴片穿墙 | 改实时阴影＋雾层伪装纵深；或在 D03 里改正交投影以降低遮挡压力 |
| 3 | 两个自定义 Pass：带状移轴模糊、局部光雾缓冲（仅覆盖揭示方向约 80 m） | 1080p 下两者叠加仍 ≥ 60 fps（M1 参考机）；雾边无硬边、不污染 UI／文字层 | 降级为全屏 tilt-shift ＋ 3 层雾片；或把雾推后到 M3 再试 |

预算：3 天 × 2 人 = **48 人时**。这 48 人时不包含在 M1 的 80 人时里——要么把 M1 从 2 周延到 2.5 周，要么从美术／内容的 M1 任务里挪。spike 的结论直接决定 D04 的 8 周 / 320 人时能否成立；**结论未出之前不要开始批量建模，也不要写游戏逻辑**。

## 2. HD-2D 的实现路径

### 场景、角色与相机

| 模块 | 实现方案 | 必须验证的边界 |
| --- | --- | --- |
| 世界 | 单路线 3D 场景，远山简化网格；完整内部按门口可见性拆包 | 路面碰撞独立，避免高模石缝影响步行 |
| 像素角色 | 脚底固定的相机朝向面片，角色视觉与胶囊控制分离；按相机相对运动向量选择 4／8 方向图集帧 | 面片完整朝相机时须用脚底锚点校正投影；不能随俯仰漂浮、穿地或以贴片参与碰撞 |
| 角色着色 | 自定义简化漫反射、天空补色与探针亮度；Alpha Clip、深度写入，提供与主 Pass 一致的深度／法线 Pass | 点采样、无损图集、无 Mipmap；透明边框不能遮住后景，树干与门框可正确遮挡人物 |
| 接触阴影 | 脚底软面片或简化代理投影，跟随地面法线 | 不用角色 Billboard 向地面投出不合理的竖板大影；斜坡不能浮空 |
| 抗锯齿 | 首选 2× MSAA，不默认启用 TAA 或时域超分 | 移动截图检查像素边缘；若全屏后期仍抹掉像素，先修角色遮罩与采样 |
| 相机 | 固定预设＋跟随、POI 机位、两段演出轨道共享一个状态管理 | FOV 28°、俯视 30°、常态距离 22 m；投影与 D03 一致，不直接换成自由旋转 |

64×80 px 画布、有效身高 56 px、32 PPU、1.75 m 世界身高与 140–180 px 常态占屏目标均沿用 [01-art-direction.md](01-art-direction.md)。MVP 为 4 方向、2 动作族、48 帧；完整地点为 8 方向、96 帧。UI 始终在原生分辨率渲染，不参与角色点采样或场景景深。

### 光雾与后期

建议执行顺序为「线性 HDR 场景与角色 → 深度雾／局部光雾 → 深度感知带状模糊 → Bloom → 调色与色调映射 → 原生 UI」。Unity 6 的自定义部分采用 Renderer Feature／Render Graph，显式声明颜色、深度与角色／POI 保护遮罩的读写；具体注入点在 M1 用帧调试器确认，不假定一张全屏材质就能按任意次序叠加。[Unity Render Graph 手册](https://docs.unity3d.com/6000.0/Documentation/Manual/urp/render-graph.html)。

常态以深度雾提供空气透视，Z05 增加近、中、远 3 层雾片；片元根据场景深度柔化交界。推荐中画质用 1/4 宽高分辨率的局部光雾缓冲，即 1080p 下 480×270，每像素沿视线最多 16 次密度采样，范围只覆盖揭示方向约 80 m；空间变化来自低频噪声，最多 1 盏方向光，不做多灯光体积阴影。

这些数值是将自定义光雾控制在约 2.4 ms 内的初始预算，不是性能保证。先做 3 层雾片和光束，再在 M3 预算内补局部体积采样；若不达标，低画质移除采样，仅保留雾片、深度雾与少量光束，仍须表现体积感和 18 秒轮廓揭开。不能因 URP 没有原生局部体积雾就把关键镜头删成白屏淡出。

带状模糊最大半径常态上 4／下 2 px，揭示上 2／下 1 px，沿用美术规定；角色、POI 和脚下路径保护遮罩参与深度判断，不能通过最后将人物无条件覆盖到画面上解决模糊，否则会失去遮挡。保护区边缘用约 2 px 过渡，测试天空与钟楼交界有无光晕。关闭景深时完全跳过该 Pass。

使用 1 盏方向光、2048² 阴影图、2 级联、60 m 阴影距离；室内最多 2 盏无阴影烛光。静态间接光在引擎烘焙，动态角色用光探针，方向光的动态雾透射不烘进 BaseColor。揭示固定曝光，改变雾而非太阳亮度；材质、光照图预算见美术文档。

## 3. Blender → 引擎的数据管线

运行模型使用 FBX 与外部贴图，源文件保留 Blender；不依赖编辑器运行时自动调用本机 Blender。若 D01 改选 Godot，导出改为官方推荐 glTF 2.0／GLB，必须重新验证材质和碰撞，不能原封不动照搬 FBX 预设。[Godot 导入格式说明](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/available_formats.html)。

| 步骤／责任 | 输入与约定 | 检查与失败处理 |
| --- | --- | --- |
| 建模／美术 | Metric、Unit Scale 1.0；应用旋转缩放，对象 Scale = 1；门槛或钟楼底座中心为根 | 先用 1 m 立方体、1.75 m 人形标尺与带正面箭头校准，不凭照片猜导入尺度 |
| 导出／美术 | FBX，-Z Forward／Y Up、Scale 1 起步；仅网格与必要空节点，不带灯光相机 | Blender Z 向上转引擎 Y 向上；引擎 +Z 为项目正面，导出选项不保证最终朝向，箭头不符则修预设后重导 |
| 几何／美术 | 显式三角化、固定法线策略、3 级 LOD；教堂外壳 60000、钟楼 20000 三角面 LOD0 上限 | 对照源与导入三角面；硬边、负缩放或法线不符则退回，不在场景临时旋转补救 |
| 材质／技术 | BaseColor 用 sRGB；Normal 与通道图用线性；粗糙度保留在源，导入转换为光滑度 | 标准 URP Lit 将金属度放 R、smoothness 放 A，AO 按所用 shader 单独或复用读 G；原始 ORM 不直接接入当 Metallic 图 |
| UV／美术＋技术 | UV0 材质；UV1 唯一、不重叠，等效 1024² 至少 8 px 岛间距起步 | 检查引擎实际光照 UV 通道，生成 UV 后复查接缝，不把 Blender UV 命名当引擎索引保证 |
| LOD／技术 | 按占屏高度约 20%、8% 切 LOD0→1→2；低于 1% 可剔除 | 揭示前固定所需 LOD 并加载；0.3 秒渐变须 shader 支持，不能默认所有材质可用 |
| 碰撞／技术 | `COL_` 标记为项目命名，显式关联独立低面碰撞 | 建筑包最多 40 个简单碰撞体；复杂门廊静态网格碰撞单包不超过 2000 三角面；不会自动识别前缀 |
| 场景光照／技术 | Blender 烘法线／AO；引擎烘最终静态间接光与探针 | 完整最多 4 张、MVP 最多 2 张 2048² 光照 atlas；MVP 选非方向性 lightmap，不另生 shadowmask，避免预算含糊 |
| 回归／双方 | 从源重导再走到门廊、切观察机位、播放揭示 | 尺度、碰撞、材质绑定和锚点不应依赖手工修导入子对象；外层场景对象承载交互数据 |

工作源 ORM 与运行打包图是不同派生文件，贴图数量以 [05-mvp.md](05-mvp.md) 的运行内容口径计数，不将派生文件重复算成新材质。若标准 URP Lit 需独立 AO 贴图，会突破每套 3 张预算；推荐统一材质 shader 读取打包 AO，或合并到项目遮蔽方案，不能悄悄加到 4 张。

命名沿用 `gergeti_church_exterior_LOD0`、`gergeti_belltower_LOD1`、`COL_gergeti_porch`、`MAT_gergeti_stone`、`T_gergeti_stone_BaseColor`。FBX 的轴向映射与材质转换能力不能替代实际校准；参考 [Blender FBX 手册](https://docs.blender.org/manual/en/4.4/addons/import_export/scene_fbx.html)。

## 4. 交互与叙事数据方案

采用 **UTF-8 JSON 外部数据作为内容源**，不把 POI 正文写在脚本或场景对象里。JSON 适合嵌套段落、出处列表和内容审核标记；CSV 适合单层翻译表，但多段正文／多来源易产生转义和列维护问题，本阶段不引入表格转换工具。这里只定义字段，不创建数据文件或示例代码。

| 数据实体 | 必需字段与类型 | 用途与约束 |
| --- | --- | --- |
| Site | `schema_version` 整数、`site_id` 字符串、`name_key`、`description_key`、`zone_ids` 数组、`entry_anchor_id`、`exit_anchor_id` | 描述地点入口与结构，ID 不随翻译变化 |
| Zone | `zone_id`、`site_id`、`order` 整数、`camera_preset_id`、`audio_profile_id`、`checkpoint_id` | 场景绑定资源 ID，不写平台绝对路径；海拔标签单独存，不由 Y 坐标换算 |
| POI | `poi_id`、`site_id`、`zone_id`、`anchor_id`、`camera_preset_id`（可空）、`title_key`、`paragraph_keys` 数组、`source_ids` 数组、`content_kind`、`review_status`、`content_revision` 整数 | 段落必须 2–4 条，内容类为史实／空间重构／观察札记；稳定 ID 关联札记 |
| 本地化 | `locale`、`strings` 键值映射；键例 `gergeti.p04.title`、`gergeti.p04.body.01` | 段落整句翻译，不把译文拼接；中文也从此读取，不作为代码默认常量 |
| 出处 | `source_id`、`institution_or_author`、`title`、`locator`、`url`（可空）、`checked_on`、`rights_note` | 正文证据和图像授权分别记录；有引用不代表可转载照片 |
| 演出配置 | `sequence_id`、`duration_seconds`、`trigger_anchor_id`、`final_state_id`、`skip_hold_seconds` | 18 秒揭示、14 秒抵达独立配置；跳过与正常结束共用最终状态 |

空间坐标与机位由场景内有稳定 ID 的锚点提供，JSON 只引用 ID，避免美术移动建筑后需要改几份坐标。POI 触发距离统一沿用 2.2／2.6 m 提示与 1.8 m 打开规则；只有记录理由的特殊对象才能覆盖。

未来内容导入时检查：ID 唯一、所有外键存在、正文段数、标题／段落长度提示、出处非空、语言键完整、场景锚点存在。开发稿可为 `draft`／`unverified`，对外构建只收 `approved`；发现未审核内容即阻止该构建，不能发布半句占位。缺译键在开发版显出键名以便定位，对外构建报错；玩家选到尚未提供的语言时回退简体中文并说明。

⚠️ 待决策 D06：推荐 MVP 只交付简体中文，但结构从第一天保留语言键；同步英文需额外翻译和约 30% 字符扩展的排版验证，手柄需补焦点导航与设备测试。延后语言不允许延后数据分离。

### 存档与更新

本地存档建议为 UTF-8 JSON，最小字段为 `save_version`、`site_id`、`checkpoint_id`、`safe_anchor_id`、`revealed`、`reveal_in_progress`、`arrival_complete`、`arrival_in_progress`、`collected_poi_ids`、`seen_content_revisions`、`journey_state`；设置另保存语言、字号、景深和镜头减弱开关。只存稳定 ID 和状态，不复制正文或序列化临时场景对象。

先写临时存档、校验后替换正式存档，保留最近 1 份有效备份；每次关键状态变化写入，禁止逐帧落盘。续玩验证锚点有效性，失败则落回当前区入口；版本变更显式迁移，删改 POI 保留旧 ID 映射。损坏时恢复备份并提示，两个存档均不可用才让玩家选择重新开始，不能静默覆盖。演出中断语义按 [03-flow.md](03-flow.md) 状态表执行。

## 5. 音频方案

使用引擎内置 AudioSource／Mixer，MVP 不引入 FMOD 或 Wwise：只有单路线、少量声层，新增中间件会多出集成、授权和打包验证。素材源建议 WAV、48 kHz／24 bit，运行压缩根据长短分组；长环境循环流式播放，短脚步与 UI 声驻留，避免边走边解码大量小文件。

| 层 | 随分区变化与参数建议 | 遮蔽／混音规则 |
| --- | --- | --- |
| 环境底层 | 镇缘、林间、草甸、岩风、云中、广场 6 个 profile；相邻约 4 秒等功率交叉淡化 | 最多同时 2 条环境循环，增益由 Zone 曲线驱动，不能拿几何 Y 值当真实海拔 |
| 近处材质 | 土、草、石 3 类脚步；每类至少 3 个变体，避免连续同一采样 | 与走路动画落脚同步，停步立即收尾；3D 衰减参考距离 1 m、最大约 12 m |
| 身体与微物件 | 轻呼吸、衣物／背包细响；呼吸阈值沿用玩法文档 | 不与风争峰值，声音可独立调低；关闭不影响移动 |
| 揭示音垫 | 1 条约 30 秒可淡出的持续音，18 秒演出后自然延续 | 不当作现场宗教声音或历史录音；允许音乐音量为 0 |
| 室内（完整） | 门口过渡到短混响与低室外风，建议混响尾约 1.2 秒起步 | 墙体遮蔽用约每 0.2 秒一次射线判断并平滑 0.3 秒，低通起点约 1.5 kHz、降低约 8 dB；MVP 无内部则不制作 |
| UI | 交互、收录短声各 1 条 | 2D 播放；打开阅读页时场景约降 6 dB，关闭恢复；不以提示音作为唯一反馈 |

建议同时不超过 24 个活动声源，其中环境／配乐流式声源不超过 3 个；依据是此场景没有人群或战斗。环境、音乐、角色、UI 与总音量各有控制，母线峰值保留约 1 dB 余量。除前方可见物体外，不使用持续宗教诵唱和定时钟声来填空；没有可靠资料就不把声景标作现场还原。

## 6. 性能目标与画质降级

以下是未来测试合同，不是当前已满足的硬件需求。Windows 为主验收，macOS 为开发与试玩验证；统一在独立运行包测量，编辑器帧率只作诊断。

| 项目 | 建议目标 | 依据与测量方式 |
| --- | --- | --- |
| Windows 参考机 | Windows 11 x64、GTX 1660 6 GB、Ryzen 5 3600（6 核）、16 GB RAM、SSD | 假设可借到同档设备，代表保守中档 PC；D04 在 M1 前落实，未测试不公布最低配置 |
| 主性能 | 1920×1080、中画质、平均至少 60 fps；帧耗时 P95 ≤20 ms、P99 ≤33.3 ms | 60 fps 单帧约 16.67 ms；分位线限制长卡顿，不以平均掩盖揭示加载 |
| macOS 试玩 | Apple Silicon M1、16 GB 统一内存；1080p 输出、低画质、平均至少 30 fps | 场景可按 0.75 比例渲染为 1440×810，UI 仍原生；为开发验证而非正式 Mac 配置承诺 |
| 显存／内存 | Windows 专用显存峰值 ≤3 GiB、进程内存 ≤4 GiB；Mac 进程常驻 ≤5 GiB，避免交换压力 | 留系统与编辑工具余量；统一内存不机械等同于 3 GiB 独立显存，分别记录 |
| 几何与绘制 | 同屏场景三角面 ≤600000、主相机批次建议 ≤250、总材质完整地点 ≤20 | 以固定相机和复用草石限制 CPU 与过绘制；批次数是诊断预算，不替代帧耗时验收 |
| 贴图与光照 | 默认 2048²、例外 4096² 需预算审核；MVP 2／完整 4 张 2048² 光照 atlas | 与美术规范一致，远景不因不可达而使用超大唯一贴图 |
| 加载与存储 | SSD 冷启动到可操作 ≤15 秒；MVP 安装包 ≤1.5 GiB、完整地点 ≤3 GiB | 以单地点少量资源估算；首次着色器／平台预热也纳入启动记录 |

1080p GPU 的初始分账建议为场景 5 ms、阴影 2 ms、角色／遮罩 0.6 ms、雾 2.4 ms、景深／Bloom／调色 1.6 ms、UI 0.4 ms，合计 12 ms，余约 4.67 ms 给波动与驱动；CPU 主线程目标 ≤6 ms。CPU 与 GPU 通常并行，不能把二者直接相加认定超预算。若瓶颈实际不同，按采样调整分账，但不放宽主性能合同。

MVP 的 30 张 2048² PBR 图若按平均 8 bit/texel 压缩并含 Mipmap 粗估约 160 MiB；角色图集约 2 MiB。这个估算只解释贴图数量可控，不等于总显存；HDR 颜色、深度、阴影、雾缓冲、驱动与资源副本必须实测。Normal 与颜色按平台选择合适压缩格式并检查画质，不能拿磁盘 PNG 大小当运行显存。

低画质依次关闭局部体积采样、降低阴影距离到 40 m／图尺寸到 1024²、减弱或关闭带状模糊，最后才降场景分辨率。3 层散雾时序、完整教堂轮廓、原生文字与前方 8 m 可读路径属于验收底线。景深关闭是所有画质都可选的可读性选项。

性能记录固定覆盖 Z02 林间、Z05 揭示、Z06 广场 3 段，每段至少 60 秒；揭示段包含触发前后并至少冷启动走一次，暖缓存再走一次。记录构建版本、硬件、分辨率、画质、平均值与分位数；首次加载卡顿单独注明，不从统计中删去。未来测试记录可写入本文件对应版本段落，本轮不创建日志或测试文件。

## 7. 版本管理、构建与开发环境

### 版本与资产管理

当前处于文档阶段：暂不建立忽略文件、LFS 配置与工程目录。设计定稿后按 [05-mvp.md](05-mvp.md) 的里程碑进入实现时建立 Git＋Git LFS：Markdown、JSON、场景／资源的文本序列化文件走普通 Git；blend、FBX、PNG、WAV 等大二进制走 LFS；缓存、临时导出和运行包不进入源码库。源模型与运行导出均保留可追溯版本，发布包放构建存储，避免反复增大 Git 历史。

Unity 未来启用可见 meta 与文本序列化，资产及 meta 一起移动提交；同一二进制资产指定单人编辑，场景按主路／建筑职责拆分以减少冲突。编辑器、URP、输入与 UI 包均锁版本，里程碑内不例行升级；只在有明确修复收益时开独立验证分支，再重跑混合遮挡和揭示检查。

### macOS 开发与 Windows 打包

macOS 建议至少 16 GB 统一内存、可用 SSD 100 GB，用于编辑器、Blender、导入缓存和双平台输出；这是小团队工作空间假设，32 GB 可减少同时开工具的压力，不能把开发内存建议当玩家最低要求。Blender 选择实现启动时受支持的稳定版本，与 Unity／导出预设一起记录；本轮不安装。

日常用 Metal 开发与试玩；主发行包为 Windows x64／DX11，先统一采用 Mono 后端制作 MVP，减少跨平台构建变量。M1 就安排一台 Windows 机器产出并运行 Windows 包，不能以 Mac 编辑器截图代替发行平台验证。未来若改 IL2CPP，必须单独验证本机原生编译工具链；Windows IL2CPP 依赖 Visual Studio C++ 工具和 Windows SDK。[Unity Windows 工具要求](https://docs.unity3d.com/6000.0/Documentation/Manual/windows-requirements-and-compatibility.html)。

每个里程碑生成 Windows x64 与 macOS arm64 两份包，资源版本相同，包含地点入口、设置、游戏内容与本地存档；内测不接商店 SDK、云存档或在线账号。构建标识记录版本、内容版本、源版本 ID 与引擎精确版本；正式验收关闭开发叠层，单独保留性能采样方式。最小流程是「校验外部数据 → 导入资产 → 打包 → 新存档走通 → 续玩／跳过／大字检查 → 性能采样」。

⚠️ 待决策 D04：推荐由技术负责人落实 Windows 验证设备与 2 人各每周 20 小时投入；若只能单人则约 16 周，若无 Windows 设备需借测或安排远程机器并增加协调成本。⚠️ 待决策 D06：MVP 的 Mac 包先用于可控试玩；公开分发应安排签名、公证及不同系统版本测试，选择公开分发会增加账号费用和打包工时，不能默认已经包含在内测包验收中。
